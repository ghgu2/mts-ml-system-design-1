# ДЗ 3 Переобучение антифрода в Apache Airflow

Проект продолжает Kafka-сервис из ДЗ‑1. Airflow по расписанию обучает CPU CatBoost, сравнивает кандидата с действующей моделью и публикует согласованный комплект `model.cbm` + `preprocessing.json`. Онлайн-сервис подхватывает его между сообщениями без перезапуска. ДЗ‑2 с ClickHouse запускается отдельно и не участвует в обучении.

## Запуск

Из корня репозитория, при работающем Docker Engine и Docker Compose v2:

```bash
docker compose up --build -d
docker compose ps -a
```

Для Docker желательно выделить 8 ГБ RAM. Первая сборка скачивает Airflow и ML-библиотеки и может занять несколько минут. Сервисы `volume-init`, `airflow-init`, `bootstrap` и `kafka-setup` должны завершиться с кодом `0`; `airflow`, `airflow-scheduler`, `postgres`, Kafka и скоринг продолжают работать. Дождитесь здорового состояния Airflow и scheduler.

| Сервис | Адрес |
|---|---|
| Airflow | http://localhost:8081 — `admin` / `admin` |
| HTML-отчёты DQ | http://localhost:8082 |
| Kafka UI | http://localhost:18080 |
| Streamlit для своих CSV | http://localhost:18501 |
| Kafka с хоста | `localhost:19095` |

Учётные данные предназначены для локального учебного запуска. Веб-порты опубликованы на `127.0.0.1`. PostgreSQL используется для метаданных Airflow и наружу не публикуется. Размеченная витрина и квитанции прогонов лежат в отдельной SQLite БД `/data/showcase.sqlite` на локальном Docker-томе. WAL, блокировка записи и транзакции позволяют supply и training безопасно работать из разных процессов; сетевые файловые системы для этой БД не поддерживаются.

## DAG и расписания

Все DAG включены при создании, `catchup=False`, `max_active_runs=1`. Запуск кнопкой Trigger DAG в UI равнозначен запуску по расписанию. Время расписания Airflow — UTC; разница часового пояса не меняет интервал в пять минут.

| DAG | Расписание | Цепочка |
|---|---|---|
| `retrain_fraud_model` | каждые 5 минут | `prepare_window` → `split_by_time` → `preprocess_training` → `train_candidate` → `evaluate_candidate` → `publish_and_commit` |
| `supply_labeled_month` | каждые 5 минут, смещение 2 минуты | `sample_month` → `append_month` → `prune_history` |
| `check_data_quality` | каждые 5 минут, смещение 4 минуты | `snapshot_quality` → `render_report` → `enforce_quality` |

Файлы `hw3/dags/` собирают граф. Функции задач находятся в `hw3/hw3_pipeline/`; docstring каждой задачи объясняет её вход, результат и поведение при повторе. Через XCom передаются только небольшие словари и пути, сами датасеты сохраняются в parquet на общем томе.

## Данные и окно обучения

Включённый `examples/hw3_train.csv` содержит 12 000 реальных строк из учебного `train.csv`: по 2 000 строк за январь–июнь 2019, пропорциональная стратификация по `target`, `random_state=42`. Всего 84 положительных примера. Данные не синтетические. Пример нужен для быстрой проверки, качество модели на нём не является оценкой качества на полном датасете.

Воспроизведение примера при установленных pandas:

```bash
python hw3/build_sample.py /путь/к/train.csv
```

Bootstrap загружает CSV ровно один раз и обучает исходную модель на январе–феврале. Март используется только для расчёта исходных метрик. Первый DAG переобучения берёт окно февраль–апрель: февраль–март идут в train, апрель — в test. Далее окно сдвигается на один месяц, сохраняя **3 календарных месяца**. Если следующего месяца ещё нет, DAG получает состояние skipped; вручную запустите supply или дождитесь расписания.

Supply берёт **10 000** случайных строк из уже имеющейся витрины, переносит время в месяц после максимального месяца витрины и добавляет батч. День 29–31 при необходимости обрезается до конца нового месяца. История ограничена **36 календарными месяцами**, включая самый новый. Если поставка обогнала обучение настолько, что очистка затронула бы ещё не обработанное окно, supply останавливается с понятной ошибкой и ждёт, пока переобучение догонит. Архивы окон для восстановления прогонов хранятся отдельно от очищаемой витрины.

Параметры `HW3_WINDOW_MONTHS`, `HW3_HISTORY_MONTHS`, `HW3_BATCH_SIZE` задаются перед `docker compose up`. После инициализации длина окна и глубина истории фиксированы для тома: для их изменения создайте новый Compose-проект с новыми томами. Размер батча можно менять без пересоздания данных.

Для полного датасета используйте отдельный проект, чтобы не переиспользовать демонстрационную витрину; сначала остановите демо из-за занятых портов:

```bash
docker compose down
HW3_INPUT_DIR=../teta-ml-1-2025 HW3_TRAIN_FILE=train.csv \
  docker compose -p mlops-hw3-full up --build -d
```

Каталог с `train.csv` можно указать абсолютным путём. Полный набор требует больше памяти и времени. Повторный старт существующего проекта сохраняет витрину, модели и указатель месяца; подмена входного CSV не перезагружает существующую БД.

## Собственный препроцессинг

`fraud_detector/src/retraining_features.py` импортируется и обучением, и онлайн-скорингом. Он отличается от семинарского: использует частоты категорий из train, циклические признаки часа и дня недели, выходной день, haversine-расстояние, логарифмы суммы/населения/расстояния и сумму на душу населения. Категории также передаются в CatBoost как строки. Пропуски числовых признаков заменяются медианами train, новая категория получает частоту 0. Имена, адреса, почтовый индекс и `target` в признаки не входят.

Медианы и частоты вычисляются **только на train**. Target encoding отсутствует. На test применяется замороженный препроцессинг кандидата либо действующей модели. Число итераций фиксировано: test не используется для early stopping, выбора параметров или порога. Обучение и inference выполняются на CPU, `thread_count=2`.

## Проверка модели перед публикацией

Кандидат и действующая модель оцениваются на **одних и тех же сырых строках самого свежего месяца окна**. Каждая применяет свой сохранённый препроцессинг. Старые метрики с другого месяца не используются для сравнения.

Публикация разрешается, только если одновременно не уменьшились:

1. Average Precision — основная метрика для редкого фрода;
2. ROC-AUC — дополнительная метрика ранжирования.

Допуск `1e-12` учитывает лишь численную погрешность. Равенство допускается. F1 при пороге **0.98** сохраняется как диагностическая метрика; порог флага скоринга остаётся таким же, как в ДЗ‑1. При одном классе, плохих данных или ошибке вычисления DAG падает без публикации. Bootstrap — единственное исключение из сравнения: действующей модели ещё нет, создаётся исходная собственная модель.

Отклонённый кандидат остаётся в `/models/candidates/<version>/` с `evaluation.json`, но в `/models/releases/` не копируется и `current.json` не меняется. Указатель обработанного месяца после успешного сохранения и оценки кандидата сдвигается и для отклонения, чтобы следующие месяцы продолжали обрабатываться. Это отдельный указатель от действующей версии модели. Решение `accepted=false` — успешный прогон DAG, а не авария.

## Повторные запуски и публикация

Версия соответствует месяцу, например `m201904`. Месяц, окно, проверочная выборка и исходная версия фиксируются в журнале. Retry или новый DAG run после ошибки продолжают тот же незавершённый месяц; очистка старой задачи не может передвинуть состояние назад. Supply фиксирует добавленные строки и квитанцию в одной SQL-транзакции, поэтому авария не оставляет половину батча и повтор не дублирует строки.

До изменения указателя проверяются бинарник, порядок признаков и SHA-256 модели/препроцессинга. Комплект сначала полностью создаётся в staging, затем атомарно переносится в `releases/`; атомарная замена `current.json` делает его видимым для сервиса. Только после сохранения кандидата и решения обновляются курсор и квитанция в транзакции SQLite. Если процесс упал между заменой файла и фиксацией транзакции, повтор узнает ту же версию и завершит запись состояния без дополнительного сдвига.

Скоринг монтирует реестр только для чтения. Между сообщениями он проверяет указатель и загружает **модель вместе с её статистиками** в новую пару объектов. Если комплект повреждён, текущая рабочая пара сохраняется, ошибка попадает в лог. Во всех результатах ДЗ‑3 есть `transaction_id`, `score`, `fraud_flag`, `model_version`. Незавершённая доставка результата в Kafka не подтверждает входное сообщение; доставка при сбоях имеет семантику at-least-once.

## Data Quality

Отдельный DAG проверяет всю текущую размеченную витрину. Перед обучением те же правила проверяют замороженное окно. Правила:

1. Все обязательные признаки и `target` присутствуют.
2. В наборе не меньше 100 строк.
3. В обязательных полях нет пропусков.
4. Время транзакции корректно разбирается.
5. Target равен 0/1, присутствуют оба класса.
6. Все числовые признаки конечны, без NaN/Inf.
7. Сумма и население неотрицательны.
8. Широта в пределах ±90, долгота ±180, включая координаты магазина.
9. Все шесть категориальных полей непустые.
10. В каждом месяце присутствуют оба класса.

HTML и JSON публикуются в `/reports` рядом с `/models`, на отдельном томе. Отчёт сначала записывается, затем `enforce_quality` завершает DAG ошибкой, если есть FAIL. Поэтому плохие данные не лишают проверяющего отчёта. История отчётов доступна на http://localhost:8082.

## Проверка результата

Полная автоматическая проверка запускает настоящие DAG через REST API Airflow, проверяет квитанцию поставки, отправляет Kafka-пробы до/после публикации и требует получить новую версию от работающего скоринга:

```bash
docker compose run --rm --no-deps verify
```

Если gate отклоняет кандидата, проверка запускает следующие месяцы (до шести попыток), не обходя gate. JSON решений и последний HTML сохраняются в `/reports/verification/` и доступны на http://localhost:8082/verification/. Автоматические расписания могут параллельно создавать дополнительные прогоны, каждый с собственным run_id. Чтобы скопировать результат на хост:

```bash
docker compose cp airflow:/reports/verification/. hw3/results/
```

Проверка retry, отклонения модели, падения в середине публикации, восстановления указателя, очистки истории, train-only статистик, hot reload и разбора DAG в том же образе:

```bash
docker compose run --rm --no-deps --entrypoint python bootstrap -m unittest discover -s /opt/airflow/tests -v
```

Ручная проверка: в Airflow запустите `retrain_fraud_model`, откройте цепочку задач, затем посмотрите `scoring` в Kafka UI. Если кандидат принят, `model_version` изменится, а контейнер скоринга продолжит работать без перезапуска. При отклонении изучите метрики, версия должна остаться прежней. Реестр и решения можно посмотреть так:

```bash
docker compose exec airflow cat /models/current.json
docker compose exec airflow ls -R /models/releases /models/candidates
docker compose logs --tail 50 fraud_detector airflow-scheduler
```

Остановка с сохранением данных: `docker compose down`. Для полного сброса **только ДЗ‑3**: `docker compose down -v`; все модели, история, метаданные Airflow и отчёты этого проекта удалятся. ДЗ‑1 использует `docker compose -f docker-compose.hw1.yml up --build -d`, ДЗ‑2 — прежний `docker-compose.hw2.yml`; их тома не затрагиваются.

Основы интеграции Airflow взяты из [семинарского проекта](https://github.com/NikitaMalykhin/mlops_realtime_fraud_detector_airflow); собственные реализация препроцессинга, quality gate, квитанций, реестра и DQ находятся в этом репозитории. Документация: [запуск Airflow 2.10.5 в Docker](https://airflow.apache.org/docs/apache-airflow/2.10.5/howto/docker-compose/index.html), [загрузка CatBoost](https://catboost.ai/docs/en/concepts/python-reference_catboost_load_model).
